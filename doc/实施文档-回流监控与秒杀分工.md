# 大麦抢票实施文档：回流监控与秒杀的分工

> 编写日期：2026-08-31
> 验证设备：MEIZU 20 Pro / Android 16 (API 36) / 1080×2400 / 大麦 APP 9.0.31
> 验证场次：成都·薛之谦"万兽之王"巡回演唱会-成都站 2026-10-02 19:00

---

## 一、核心结论（先看这个）

**控件自动化脚本只适用于「监控回流票」，不适用于「开售秒杀」。**

| 场景 | 用什么 | 为什么 |
|---|---|---|
| **开售瞬间秒杀** | **人工手动** + 大麦官方「预约想看」 | 见 §二。脚本对熟练手动只有 1~3 秒优势，而胜负由服务端排队和库存决定，不由客户端点击速度决定 |
| **开售后刷回流票** | **控件自动化脚本**（`./launch_monitor.sh`） | 见 §三。回流票是随机零散出现的，需要连续几小时每 20 秒刷一次——这是人做不到、脚本不可替代的场景 |
| API 直接下单 | 不做 | 需要逆向大麦 mtop 私有协议并伪造签名，属于绕过平台风控。本项目不实现 |

## 二、为什么秒杀不能靠控件脚本

### 2.1 速度优势没有想象中大

控件自动化（Appium / AutoX.js）都建立在 Android 无障碍服务（AccessibilityService）之上，链路是：

```
APP 绘制界面 → 系统把控件树推给无障碍服务 → 脚本在树上匹配 → performAction/dispatchGesture 注入点击
```

实测数据（2026-08-31，本机 + MEIZU 20 Pro）：

- Appium 建立 session：**4.1 秒**（所以必须提前预热，v3 daemon 就是为此设计）
- 单次 `find_element`：几十 ~ 几百毫秒
- 系统推送控件树本身有 **50~150ms 滞后**，页面刚变时可能读到旧树

熟练手动在「已预约、页面自动勾选」的前提下，从点「立即购买」到「提交订单」约 2~4 秒。
**脚本快 1~3 秒，是同一量级，不是数量级差异。**

### 2.2 胜负不在客户端

大麦开售是**服务端排队 + 库存扣减**，不是客户端先点先得。抢不到的主因是排队序位、风控拦截、库存瞬间清零，不是慢了 200ms。

### 2.3 本次实测发现的硬伤：控件没有文本

大麦 9.0.31 的**场次和票档是自绘控件，无障碍树里 `text` 属性为空**。

`uiautomator dump` 实测结果：整页只有「休 / 班 / 预售 / 可预约 / 取消预约」这些角标有文字，
`看台517元`、`2026-10-02` 这类关键信息**完全读不到**。

后果：

- 所有 `text("看台517元")` / `text("2026-10-02")` 形式的匹配**必然失败**
- 只能退化到 **index 序号** 或 **绝对坐标** 定位
- 而 index 是按「当前屏幕可见节点」排的（见 §四风险 1），坐标则受布局影响

在秒杀这种一次性、不容错的场景里，靠 index/坐标盲点风险过高。

### 2.4 脚本和人会互相干扰

无障碍脚本注入的点击与人的手指操作**抢同一个焦点**。开抢时若两者同时操作同一台手机，脚本点了「下一步」而你的手指点在别处，两边都会乱。

**所以：秒杀时只用人工，不要同时挂脚本。**

## 三、回流监控：脚本不可替代的场景

### 3.1 回流票是什么

开售后仍会有零散票释放：用户退票、下单后超时未付款自动释放、主办方补放。这些票**出现时间随机、存在窗口只有几秒到几十秒**。

人无法连续几小时每 20 秒刷一次页面，脚本可以。

### 3.2 一键启动

```bash
cd ~/IdeaProjects/ticket-purchase
./launch_monitor.sh          # 默认 20 秒轮询
./launch_monitor.sh 10       # 改成 10 秒轮询
```

脚本会自动完成：

1. **环境自检** —— adb / poetry / 设备在线状态（区分 unauthorized / offline / 未连接三种情况并给出对应修复提示）
2. **页面状态检查** —— 确认大麦停在 SKU 票档页，不在则告警
3. **防锁屏** —— 自动执行 `svc power stayon usb`，USB 供电时屏幕常亮（锁屏会导致读不到控件）
4. **启动监控** —— 每轮 `adb shell uiautomator dump` 解析票档容器

### 3.3 三种状态识别

监控会把每个票档判成三态之一：

| 状态 | 判据 | 行为 |
|---|---|---|
| **预约态** | 含「可预约 / 已预约 / 即将开售」 | 还没开售，继续等（不报警） |
| **售罄** | 含「缺货登记 / 已售罄 / 无票」 | 有票位无票，继续刷 |
| **可购** | 既不售罄也非预约态 | **报警**：macOS 通知 + 终端响铃 + 高亮，持续每轮提醒 |

> ⚠️ 「预约态」这一档是 2026-08-31 补上的。原实现只判售罄，导致预约期内每轮把 7 个票档全报成"可购"——
> 实测第一轮就假警报并退出，等于完全没有监控。

### 3.4 报警后怎么办

**脚本不会自动下单，报警后你手动接管。** 因为：

- 回流票窗口虽短但仍有几秒到几十秒，够人操作
- 自动下单一旦点错票档，是真实付款损失
- 手动确认还能避开验证码/滑块卡死

### 3.5 收尾

```bash
./stop_daemon.sh                                  # 停 daemon，保留 Appium
./cleanup.sh -y                                   # 完全收工：杀 Appium + 清临时 + 复位安全开关
adb shell svc power stayon false                  # 还原常亮设置
```

## 四、已知风险（必读）

### 风险 1：index 定位随滚动位置漂移 ⚠️

`price_index` / `perform_index` 用的 `UiSelector().index(N)` 是按**当前屏幕上可见的节点**排序，不是按数据顺序。

2026-08-31 实测证据：场次容器里 `index(0)` 的 bounds 是 `[58,205][1022,249]`，只有 44px 高——
那是 `2026-10-01` 那行**被顶部截掉后露出的一小条**。页面再往下滑一点，10-01 完全移出屏幕后，
`index(0)` 就变成 10-02，配置 `perform_index=1` 会点到 **10-03**。

**应对**：

- `perform_index` 已设为 `null`（不主动选场次），依赖预约自动勾选或人工选定
- `price_index` 每次实际使用前**必须重新验证**，方法见 §五

### 风险 2：SKU 页底部按钮在预约态是「已预约」

v3 流程原本会点底部按钮进入 SKU 页。若脚本启动时已经停在 SKU 页，再点底部按钮
**会触发取消预约**。

**应对**：已在 `damai_app_v3_daemon.py` 加入 SKU 页分支识别——
检测到 `NcovSkuActivity` 时跳过城市选择和底部入口点击。

### 风险 3：大麦可能检测无障碍服务

枚举已启用的 AccessibilityService 是标准反自动化手段。脚本长期挂机存在被识别的可能。

### 风险 4：固定 sleep 推进

脚本用固定 `sleep(800)` / `sleep(500)` 推进流程，网络卡顿时会跑到页面前面去点空。

## 五、price_index 验证方法（每次使用前必做）

```bash

export ANDROID_SDK_ROOT="$ANDROID_HOME"
```

输出会列出票档容器内每个 index 对应的 bounds。**拿它和手机截图逐个对照**，确认

## 附录：为什么不走 API 下单（2026-08-31 GitHub 全量调研）

调研了 GitHub 上 24 个大麦抢票相关仓库，结论：**不存在当前仍可用的、纯 API 直接下单的开源方案。**

### 关键事实

- star 数较高且近期仍在更新的项目，**无一例外都是 UI 自动化**（Appium / uiautomator2 / AutoX.js / Shizuku 无障碍）
- 曾经"直接调接口"的项目全部停在 2023~2024 年，且被作者自己标记失效

| 项目 | Stars | 状态 | 作者原话 |
|---|---|---|---|
| shiyutim/tickets | 3202 | ❌ 2024-05 停更 | issue：「最近好像 h5 彻底废了」「网页通道都寄了」 |
| MakiNaruto/Automatic_ticket_purchase | 5622 | ❌ 2024-03 | README 首行「已停止维护，购买方式已迁移至手机端」 |
| gxh27954/damai_requests | 265 | ❌ 2023-09 | 更新日志：9/24「已解决可正常下单」→ 9/27「出新版验证码，接口失效」 |
| DracoYan-111/damai_grab_votes | 447 | ❌ archived | 「大麦客户端更新了，**自己几个号也被封了**，项目已无法使用」 |
| currycan/HaTickets | 431 | ✅ 唯一维护良好 | 明确写：Web/Selenium 方案**已删除**，H5/mtop 接口路线**已被官方限制，视为不可用** |

### 技术上为什么不可行

大麦有两条通道，签名机制不同，两条都堵死：

**H5 通道** —— 签名不依赖 native 库，但依赖浏览器现场环境。所谓"API 抢票"项目的实际做法是：
从用户粘贴的 cookie 里取 `_m_h5_tk` 派生签名，**再加载阿里的风控 JS 现场生成 `bx-ua` / `bx-umidtoken`**。
即：**是"借"用户已登录会话的 token，不是复现了签名算法**。而且大麦已把主要商品的购买通道收到 APP，
H5 侧普遍返回「该渠道不支持购票」，这条路从源头断粮。

**APP 通道（mtop）** —— `x-sign` / `wua` / `x-sgext` 由阿里 SecurityGuard 安全 SDK（native so）
在 APP 进程内生成。唯一获取方式是**让真实 APP 跑起来再 hook 它**。
全 GitHub 相关的公开逆向工作只有 `ylcangel/crack_libsgmain`（120 stars，**最后更新 2020-06**），早已过时。

**决定性的推论**：任何走 APP 接口的方案，都必然退化成「必须有一台跑着大麦 APP 的真机 + Frida hook」。
**而此时你已经拥有真机了** —— 直接做 UI 自动化的工程代价远低于维护 hook 链路。
这正是所有存活项目最终都收敛到 uiautomator2/Appium 的根本原因。

### 失效原因归纳

1. 购买通道从 H5 收窄到 APP，API 派项目从源头断粮
2. 风控 token（`bx-ua`/`x-sign` 等）无法离线生成，脚本侧只能"借"不能"造"
3. 多层风控叠加：设备指纹、行为轨迹、云服务器 IP 整段限制、滑块、账号权重、Root/模拟器检测
4. 验证码与接口版本迭代快于开源维护节奏（gxh27954 三天内从"可下单"变"失效"）
5. 封号成本让作者主动退场
6. 有效经验转入付费闭环（社群 ¥99~124 入群、¥1099/0.5h 咨询），GitHub 公开代码持续劣化

**结论：API 路线不仅是合规问题，工程上也已经走不通。本项目维持 UI 自动化 + 人工秒杀的分工。**
